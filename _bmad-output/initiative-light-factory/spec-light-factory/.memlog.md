- (note) Create run. Inputs: brief-light-factory.md + addendum.md (upstream bmad-product-brief) and architecture-light-factory.md (upstream bmad-architecture, 11 ADs, status final). Both pre-sorted/structured — trusting authored separation per Operation.
- (decision) Why (kernel): AI agents now generate more code than a developer can responsibly review line-by-line, so review quality either rubber-stamps or bottlenecks. light-factory proves code-level quality mechanically (build, tests, lint, security, independent agent review) so human judgment concentrates on task breakdown, design soundness, and acceptance-criteria fit.
- (capability) CAP-1 Intake validation. Intent: verify a submitted story .md file has sufficient completeness and scope before triggering agent work. Success: run halts with a clear reason on an incomplete/out-of-scope story; proceeds when intake passes.
- (capability) CAP-2 Agent analysis and plan proposal. Intent: an agent analyzes the story, proposes a solution, derives subtasks and tests, runs a clarification loop on open questions, and documents decisions as they resolve. Success: plan.md and decisions.md are produced with no unresolved open question before the plan-approval gate.
- (capability) CAP-3 Plan-approval human gate. Intent: pipeline pauses for the requesting developer to review and confirm the proposed plan before any code is written. Success: no implementation commit exists until explicit approval is recorded; the same run resumes on approval via GitHub Environment protection; a reject is terminal for that run.
- (capability) CAP-4 Scoped implementation. Intent: implementation agent writes the confirmed plan's code in an isolated branch/workspace, write access scoped to only that branch. Success: all implementation commits land on the isolated branch; the implementation agent's tool/token permissions cannot write outside it or touch other stages' state files.
- (capability) CAP-5 Automated mechanical checks. Intent: build, test, lint, and security checks run as direct CI pipeline steps against the implementation, never delegated to an agent. Success: pass/fail per check is recorded in evidence/checks/ before review proceeds.
- (capability) CAP-6 Independent agent review. Intent: a review agent distinct from the implementer, read-only permissioned, evaluates the implementation against the plan and acceptance criteria. Success: review.md is produced using only read access -- no write/edit tool available to this invocation -- with findings or a clean pass.
- (capability) CAP-7 Bounded fix loop. Intent: review findings route back to the implementation agent to fix, re-running only affected checks, hard-capped at 2 cycles tracked by the orchestration graph alone. Success: on the 2nd unresolved review the loop stops and routes to evidence-approval with status unresolved-after-cap instead of looping again.
- (capability) CAP-8 Evidence-approval human gate. Intent: pipeline pauses and presents the developer a concise summary of check/coverage metrics plus a drillable PR/diff for an evidence-based approval decision. Success: developer can decide from the summary alone and open full diff/PR only on demand; a change-request decision ends the run (reject is terminal, re-trigger needed); approval proceeds to merge.
- (capability) CAP-9 Approval and merge. Intent: upon developer approval at evidence-approval, the branch merges to target, completing the v1 loop. Success: merge happens only after explicit recorded approval; no agent invocation holds merge/admin tooling.
- (constraint) Agent runtime is Claude Code for v1 only, authenticated via subscription CLAUDE_CODE_OAUTH_TOKEN generated by 'claude setup-token' (not ANTHROPIC_API_KEY, not the /install-github-app flow). Distinct custom skills per job type (analysis, implementation, review), not one general agent. [architecture AD-9]
- (constraint) Pipeline is one GitHub Actions workflow, one triggered run, jobs chained via needs:. GitHub Environment + required-reviewers protection rules (canonical names plan-approval, evidence-approval) own the two human-wait gates as job boundaries; LangGraph (Python) owns in-job agent orchestration only within a job's own lifetime. [architecture AD-2, AD-6]
- (constraint) Ships as a blueprint/template copied into each target repo, not a dedicated orchestrating repo. light_factory/ and .claude/skills/ must never reference .github/workflows/-specific constructs, so the orchestration layer stays portable to a future dedicated orchestrator. [architecture AD-1]
- (constraint) No hosted orchestration server (Camunda/Zeebe, Temporal) for v1 -- contradicts the blueprint/minimal-footprint PoC goal. [architecture AD-3]
- (constraint) Deterministic checks (build, test, lint, security) run as direct pipeline steps, never delegated to an agent -- keeps the pipeline fast, auditable, and cheap.
- (constraint) Least privilege is enforced at two independent layers for every agent invocation, neither sufficient alone: (1) Claude Code tool-allowlist scoped to the isolated branch AND to that stage's own state-file paths; (2) GitHub token/branch-protection scoping blocking direct push to main and requiring PR+checks. No agent invocation ever holds merge/admin tools. [architecture AD-5]
- (constraint) State lives at .light-factory/<story-slug>/, one file per stage (plan.md, decisions.md, review.md, evidence/checks/, evidence/review/), append-only ownership -- no stage mutates another stage's file. Shared frontmatter schema (schema_version, story_slug, stage, status, updated) is the single source of truth for both human and orchestration script. story-slug is computed once in the first job and threaded via needs: outputs, never re-derived. [architecture AD-8, AD-10]
- (constraint) Fix loop is hard-capped at 2 cycles; the counter is incremented only by the orchestration graph's loop-control node, never by an agent. Cap hit routes to evidence-approval with status unresolved-after-cap rather than looping again -- guardrail against runaway AI spend. [architecture AD-11]
- (constraint) A reject at either gate (plan-approval or evidence-approval) is terminal for that run -- no automatic same-run loop-back. A change request means the human re-triggers the pipeline as a new run, consistent with v1's manual-trigger-only model. [architecture AD-2]
- (constraint) v1 external dependencies are GitHub (repo, Actions, Environments) and Anthropic/Claude Code only -- no ticket system or chat integration. [architecture AD-7]
- (decision) Non-goals (v1, deferred not rejected): staging deployment and controlled production rollout automation; swappable AI providers/models; alternative trigger mechanisms (issue labels, PR-linked stories, watched folders, ticket-system webhooks -- manual trigger only); multi-role approval workflows (single requesting-developer role holds all 3 gates); zero-manual-code-edits enforcement (post-v1 goal); ticket-system and chat integrations; migration to a dedicated orchestrating repo; Temporal/Camunda as an orchestration upgrade.
- (decision) Success signal (v1): demonstrable when a real story run completes end-to-end to merge with both gates exercised; mechanical checks (build/test/lint/security) run as pipeline steps with zero agent turns spent on them; the fix loop never exceeds 2 cycles on any run; and the requesting developer approves from the gate summary alone in the common case, opening the full PR/diff only when something looks off (not re-reading it by default).
