- (decision) Core thesis: AI-generated code volume exceeds what a developer can review at code level; system enforces code-level quality (coverage, architecture conformance, coding guidelines) automatically so human review shifts to outcome level (task breakdown, design notes, acceptance-criteria coverage, pipeline success).
- (decision) Form factor: internal tool for the team, deployed either as a dedicated GitHub repo with pipelines, or as a blueprint/template integrated into a new or existing software project.
- (decision) Primary audience is internal use by the team; secondary possible use is as a pitch asset. Not building for external/public launch now.
- (decision) Agent runtime: Claude Code-based agents for v1. Swapping AI provider/model is a desirable future property, not a v1 requirement. Distinct custom skills per job type (design, coding, review) rather than one generic agent.
- (decision) v1 trigger: manually started GitHub pipeline; input is a user story as a .md file already committed in the repo. Other trigger mechanisms (issue label, PR-linked story, watched intake folder, ticket-system webhook) noted as future options, explicitly deferred.
- (decision) All three human checkpoints (plan confirmation, evidence/result review, final approval) are held by a single role: the requesting developer. No multi-role approval workflow in v1.
- (decision) Evidence-review gate design: human is given metrics (coverage, pipeline/check results) plus an open PR/diff available for detailed inspection on demand, not a dashboard alone.
- (decision) v1 scope is a slim MVP covering the full loop through merge: intake check, agent analysis, clarification loop, human plan confirmation, implementation in isolated branch, automated checks (build/test/lint/security), independent agent review, fix loop, human evidence review, approval, merge. Staging deploy and controlled production rollout are explicitly deferred past v1.
- (decision) Intake 'Berechtigungen' step is about least-privilege scoping of each AGENT invocation (not end-user role/access control): every agent run gets only the minimal permission set its specific job requires (e.g. review agent read-only, implementation agent write scoped to its isolated branch/workspace, no agent holds merge rights). This is a v1 design principle, not deferred hardening.
- (event) Landscape research: no existing product combines intake/scope check + documented clarification loop + plan-confirmation gate + isolated build + automated checks + independent review agent (distinct from implementer) + human evidence review + staged rollout into one governed pipeline. Closest comparables: Devin and Amazon Kiro (checkpoint-as-product framing, front-half plan gate), GitHub Copilot review agent and Google Jules (back-half independent review / CI-autofix), Factory.ai (closest full-pipeline competitor but checkpoint-configurable not checkpoint-by-design). 2026 industry framing calls this 'governed autonomy'; ~73% of AI-touched changes still get human review somewhere.
- (decision) v1 success criteria: (1) team trusts a green pipeline enough to not re-read the diff by default, PR/diff stays available for drill-down only when something looks off; (2) pipeline runs cost-efficiently, does not waste AI credits.
- (decision) Near-term goal (post-v1, after a few iterations, not MVP itself and not 2-3yr vision): zero manual code edits — all code in the repo is authored by AI agents through the pipeline, no direct hand-edits.
- (decision) Design principle: deterministic/mechanical checks (build, tests, linting, security scans) run as direct pipeline/CI steps, not delegated to an agent to execute -- agents are reserved for judgment work (analysis, design, review, fixing findings).
- (decision) Design principle: review-fix loop is bounded (e.g. cap at 2 cycles) rather than open-ended, as a guardrail against runaway AI spend.
