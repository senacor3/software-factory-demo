- (technique) started Kill the Crown Jewel
- (idea by user) Custom UI showing per-story pipeline state (analysis/implementation/review/etc.) with built-in approval action
- (idea by user) Fork: either (A) build an integration/wire between the UI and the GitHub pipeline, or (B) ditch GitHub Actions as the orchestrator entirely and run the workflow independently, with GitHub Actions only executing individual steps (e.g. implementation) as dedicated jobs
- (decision by user) Go deeper on Branch B: orchestrator lives outside GitHub Actions, GH Actions becomes a step-runner
- (idea by user) Orchestrator runs as an AWS serverless function (Lambda), woken by GitHub webhooks
- (idea by user) UI talks to the orchestrator directly via API Gateway in front of the Lambda (not via a GitHub detour)
- (idea by user) Completion callback: the GitHub Actions job calls the Lambda via API Gateway too (a webhook-style call) when it finishes, so the orchestrator advances
- (idea by user) Substitute 1: branch protection required status checks (free-tier native) instead of environment required-reviewers
- (idea by user) Substitute 2: split the one pipeline into separate per-stage workflows; the human gate becomes manually triggering the next workflow (workflow_dispatch), gated only by normal repo write-access permissions
- (insight by user) Two distinct gates needed: Gate 1 between analysis/planning and implementation (review/verify the plan); Gate 2 as final review before merge
- (direction by user) Reject splitting plan review into a separate plan-only PR: Gate 1's review covers the story, the implementation plan, and subtasks together, and should stay tied to the implementation work, not split off
- (insight by user) After Gate 2, merging is not a plain branch-protection merge: there's a more advanced step where an agent resolves merge conflicts instead of a human
- (idea by coach) Adapt: Dependabot/Renovate-style auto-merge bot pattern (wait for a signal e.g. checks green, then act on the PR) — swap the signal for human-approval and the action for agent conflict-resolution-and-merge
- (direction by user) Gate 1 (plan review before implementation) is the critical gate, more important than Gate 2 (final merge review)
- (idea by coach) Adapt Gate 1 to the Atlantis/Terraform Cloud VCS pattern: plan output auto-posted as a PR comment, human's PR comment (e.g. 'apply') or reaction is the approval trigger that kicks off implementation
- (insight by user) Comment-based trigger has an advantage over a simple click: it naturally supports a fix loop (e.g. 'rework the plan') not just binary approve/reject
- (idea by coach) PR-comment command grammar for Gate 1: /approve resumes to implementation, /rework <feedback> loops back to analysis node with the comment text as input, /reject cancels the story
- (technique) started Nature's Solutions
- (idea by coach) Nature's Solutions: cell cycle checkpoint (G1/S, G2/M) — pause, check DNA for damage, three outcomes: repair-and-proceed, proceed-clean, or self-destruct (apoptosis) if irreparable
- (technique) started Chaos Engineering
- (idea by user) Chaos Engineering break: GitHub Actions account/usage limits (concurrency, rate limits) could be an issue, more than raw AWS/GitHub infra reliability
- (idea by coach) Sharper break: workflow_dispatch API doesn't return a run ID, so under concurrency the Lambda can't reliably correlate which GH Actions run/completion-webhook belongs to which story's state
- (idea by user) Fix: pass a unique branch name as the correlation key for workflow_dispatch, so the completion webhook can be matched back to the right story
- (idea by user) Mitigation for double/duplicate Lambda invocation: check the PR's actual current state when Lambda execution starts (not just trust the event), persist state in a database too; double execution itself is fine as long as the implementation step is tolerant of it and doesn't break
- (decision by user) MoSCoW convergence: move custom UI dashboard from Could to Must — wanted from day one
- (decision by coach) MoSCoW final: Must = [custom orchestrator outside GH Actions (Lambda+API Gateway), Gate 1 PR-comment command grammar (/approve /rework /reject), unique-branch-name correlation key, idempotent state-check-on-entry, custom UI dashboard]; Should = [Gate 2 via native branch-protection PR approval, agent-driven merge-conflict resolution, DynamoDB checkpoint state]; Could = [Checks API as extra native signal, Dependabot/Renovate-style framing for Gate 2 merge]; Won't = [GitHub required-reviewers environment protection, separate plan-only PR, cell-cycle-checkpoint framing]
- (question by user) Now that the custom UI is a Must, where should Gate 1 approval actually happen — GitHub PR comments, or inside the UI?
- (decision by user) Approval surface resolved: Option C — UI is the primary surface for developers, but its approve/rework/reject actions call the GitHub API to post the actual PR comment on the human's behalf; the webhook-to-Lambda path and the PR thread stay the source of truth/audit trail
- (insight by user) User's read: the custom orchestrator + UI is the real winner; GitHub account/concurrency limits no longer a real concern; the per-stage-workflow native trick only works with a UI/orchestrator in front of it
- (insight) Synthesis: the per-stage-workflow/workflow_dispatch native trick (SCAMPER) isn't a competing alternative — it's the actual mechanism the custom orchestrator (Branch B) uses to drive GitHub Actions; the branch-name correlation key and idempotent-on-entry checks (Chaos Engineering) are the hardening that makes running many stories concurrently through one central orchestrator safe. Chosen direction: custom Lambda+API Gateway orchestrator with a day-one UI that posts GitHub PR comments on the user's behalf (Option C), Gate 1 as a PR-comment command grammar (/approve, /rework, /reject), Gate 2 via native branch-protection PR approval plus agent-driven merge-conflict resolution
