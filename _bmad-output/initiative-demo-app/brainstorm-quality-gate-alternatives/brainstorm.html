Killing the Crown Jewel

Four techniques, two voices, one question: how do you pause a CI/CD pipeline for a human when GitHub's own gate won't let you in?

GitHub's required-reviewers environment-protection rule — the clean, built-in way to stop a pipeline and wait for a person — is locked behind Enterprise or public repositories. The software-factory pipeline runs on neither. This session took that constraint apart, technique by technique, until a human gate emerged that didn't need GitHub's permission to exist.

Technique 01

Kill the Crown Jewel

Reframe the constraint: what if the gate never had to live inside GitHub Actions at all?

The crown jewel being killed was an assumption — that a human gate has to be a feature GitHub grants you. Kill it, and the question stops being "how do we unlock environment protection rules" and becomes "what else could pause a pipeline for a person?"

Ideaby user

A custom UI showing per-story pipeline state — analysis, implementation, review, and so on — with a built-in approval action.

The Fork

Branch A

Build an integration / wire between the custom UI and the existing GitHub pipeline.

not taken
Branch B

Ditch GitHub Actions as the orchestrator entirely. Run the workflow independently; GitHub Actions only executes individual steps (e.g. implementation) as dedicated jobs.

chosen — go deeper
Ideaby user

The orchestrator runs as an AWS serverless function (Lambda), woken by GitHub webhooks.

Ideaby user

The UI talks to the orchestrator directly via API Gateway in front of the Lambda — no detour through GitHub.

Ideaby user

Completion callback: the GitHub Actions job calls the Lambda via API Gateway too (a webhook-style call) when it finishes, so the orchestrator advances.

Substitute — native GitHub stand-ins

Substitute 1by user

Branch protection required status checks (free-tier native) instead of environment required-reviewers.

Substitute 2by user

Split the one pipeline into separate per-stage workflows; the human gate becomes manually triggering the next workflow (workflow_dispatch), gated only by normal repo write-access permissions.

Insightby user

Two distinct gates are needed: Gate 1 between analysis/planning and implementation (review the plan); Gate 2 as the final review before merge.

Directionby user

Reject splitting plan review into a separate plan-only PR — Gate 1's review covers the story, the implementation plan, and subtasks together, and should stay tied to the implementation work, not split off.

Insightby user

After Gate 2, merging isn't a plain branch-protection merge — there's a more advanced step where an agent resolves merge conflicts instead of a human.

Adapt — patterns borrowed from elsewhere

Adaptby coach

Dependabot / Renovate-style auto-merge bot pattern — wait for a signal (e.g. checks green), then act on the PR. Swap the signal for human approval and the action for agent conflict-resolution-and-merge.

Directionby user

Gate 1 (plan review before implementation) is the critical gate — more important than Gate 2 (final merge review).

Adaptby coach

The Atlantis / Terraform Cloud VCS pattern: plan output auto-posted as a PR comment; the human's PR comment (e.g. "apply") or reaction is the approval trigger that kicks off implementation.

Insightby user

A comment-based trigger has an advantage over a simple click: it naturally supports a fix loop (e.g. "rework the plan"), not just binary approve/reject.

Ideaby coach

PR-comment command grammar for Gate 1: /approve resumes to implementation, /rework <feedback> loops back to analysis with the comment text as input, /reject cancels the story.

Technique 03

Nature's Solutions

Biomimicry: does biology already have a checkpoint pattern worth stealing?

⊘ dead end — tried, didn't spark
Ideaby coach

The cell cycle checkpoint — G1/S, G2/M. Pause. Check the DNA for damage. Three outcomes: repair-and-proceed, proceed-clean, or self-destruct (apoptosis) if the damage is irreparable.

One idea, one technique, no follow-on. The biology is elegant, but nothing in the session built on it — no substitutes, no adaptations, no forks grew from here. It resurfaces once more at convergence, on the Won't list, exactly where this keepsake leaves it: tried honestly, left behind honestly.

Technique 04

Chaos Engineering

Stress-test the design in progress on purpose — where does it actually break?

candidate break
Ideaby user

GitHub Actions account/usage limits (concurrency, rate limits) could be an issue — more than raw AWS/GitHub infra reliability.

sharper break
Ideaby coach

The workflow_dispatch API doesn't return a run ID — under concurrency, the Lambda can't reliably correlate which GitHub Actions run / completion webhook belongs to which story's state.

fix
Ideaby user

Pass a unique branch name as the correlation key for workflow_dispatch, so the completion webhook can be matched back to the right story.

mitigation
Ideaby user

Check the PR's actual current state when Lambda execution starts (don't just trust the event); persist state in a database too. Double execution itself is fine as long as the implementation step tolerates it.

★ Convergence

Where It Landed

MoSCoW sorted the pile. Then one more pass resolved the last open question.

Must

  • Custom orchestrator outside GitHub Actions (Lambda + API Gateway)
  • Gate 1 PR-comment command grammar (/approve, /rework, /reject)
  • Unique-branch-name correlation key
  • Idempotent state-check-on-entry
  • Custom UI dashboard

Should

  • Gate 2 via native branch-protection PR approval
  • Agent-driven merge-conflict resolution
  • DynamoDB checkpoint state

Could

  • Checks API as an extra native signal
  • Dependabot/Renovate-style framing for the Gate 2 merge

Won't

  • GitHub required-reviewers environment protection
  • Separate plan-only PR
  • Cell-cycle-checkpoint framing
Decisionby user

Move the custom UI dashboard from Could to Must — wanted from day one.

Questionby user

Now that the custom UI is a Must, where should Gate 1 approval actually happen — GitHub PR comments, or inside the UI?

Decisionby user

Option C, resolved: the UI is the primary surface for developers, but its approve/rework/reject actions call the GitHub API to post the actual PR comment on the human's behalf. The webhook-to-Lambda path and the PR thread stay the source of truth and audit trail.

Insightby user

The custom orchestrator + UI is the real winner. GitHub account/concurrency limits are no longer a real concern — the per-stage-workflow native trick only works with a UI/orchestrator in front of it anyway.

Session synthesis

The per-stage-workflow / workflow_dispatch native trick from SCAMPER isn't a competing alternative — it's the actual mechanism the custom orchestrator (Branch B) uses to drive GitHub Actions. The branch-name correlation key and idempotent-on-entry checks from Chaos Engineering are the hardening that makes running many stories concurrently through one central orchestrator safe. Chosen direction: a custom Lambda + API Gateway orchestrator with a day-one UI that posts GitHub PR comments on the user's behalf (Option C); Gate 1 as a PR-comment command grammar (/approve, /rework, /reject); Gate 2 via native branch-protection PR approval plus agent-driven merge-conflict resolution.

The converged architecture — GitHub Actions demoted from driver to step runner.
